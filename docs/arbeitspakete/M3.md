# Arbeitspaket M3 – Designer, Objektinspektor

Siehe konzept-natter.md, Abschnitt 20, 7.6 (Objektinspektor), 7.7
(Designer), 4.3/4.4 (Codegenerierung). Kleinteilig wie M1/M2.

## Abnahmekriterium (aus dem Konzept)

Ampel komplett in der IDE erstellen, alle Eigenschaften nur über den
Inspektor gesetzt.

## Reihenfolge

Objektinspektor zuerst, weil er direkt auf dem bestehenden
`pcl.properties`-Introspektionsmechanismus (`eigenschaften()`/
`ereignisse()`) aufbaut und ohne Designer-Canvas allein schon sinnvoll
und testbar ist. Der Designer (Canvas, Drag&Drop, Undo) danach, dann die
Verbindung beider plus Komponentenpalette, zuletzt die
Ereignis-Codegenerierung (libcst) für Doppelklick → Methode.

### 1. Objektinspektor: Eigenschaften lesen/setzen — erledigt

- [x] `ide/inspector/eigenschaften_tabelle.py`: `EigenschaftenTabelle`
  (Name, Wert) aus `pcl.properties.eigenschaften(typ(komponente))`;
  Zelle bearbeiten → `setattr(komponente, name, wert)` (Live-Wirkung, da
  `Prop.__set__` sofort das Qt-Widget aktualisiert, Abschnitt 5.0)
- [x] Editor je Typ passend zum `Prop.typ`: `bool` → echtes
  Kontrollkästchen (`ItemIsUserCheckable`, nicht editierbarer Text),
  `str`/`int`/`float` → Textfeld mit Typumwandlung beim Verlassen der
  Zelle
- [x] Falscher Wert (z. B. Text in Zahlenfeld) → Umwandlungsfehler bzw.
  `NatterPropertyError` abgefangen, Zelle wird auf den echten
  Komponentenwert zurückgesetzt, `fehlertext`-Attribut gesetzt (Bindung
  an den Hilfebereich folgt mit Schritt 2, sobald der Objektinspektor
  als Ganzes im Hauptfenster eingehängt ist)
- [x] Tests (`tests/test_eigenschaften_tabelle.py`, 6 Tests): Live-
  Bearbeitung ändert Komponente und Qt-Widget gleichermaßen, ungültige
  Zahl wird abgelehnt und zurückgesetzt, Kontrollkästchen für `bool`

### 4. Designer-Canvas: Platzieren, Verschieben, Größe ändern — erledigt (bis auf Palette)

- [x] `ide/designer/pfm_schreiben.py`: `pfm_aus_formular()`/
  `formular_als_pfm_speichern()` – Gegenstück zu `ide.codegen.design`,
  serialisiert ein bearbeitetes Formular zurück in eine `.pfm` (nur
  Werte, die vom Standardwert abweichen, Abschnitt 4.2), validiert gegen
  `schemas/pfm.schema.json`
- **Bug gefunden und behoben:** die Platzhalter-Handler in
  `ide/designer/laden.py` waren anonyme Lambdas (`__name__ ==
  "<lambda>"`); beim Zurückschreiben landete dieser Name in der `.pfm`
  und der nächste `design_code_erzeugen()`-Lauf erzeugte ungültiges
  Python (`self.on_create = self.<lambda>`). Behoben durch benannte
  Platzhalterfunktionen; Regressionstest in
  `tests/test_designer_laden.py`
- [x] Tests (`tests/test_pfm_schreiben.py`, 4 Tests): Rundreise gegen
  die echte `beispielprojekte/Ampel/u_main.pfm` ohne Änderung, geänderte
  Eigenschaft erscheint im Ergebnis, Standardwerte werden nicht
  gespeichert, gespeicherte Datei lässt sich wieder laden
- [x] `DesignerCanvas.verschieben()`/`groesse_aendern()` (Mindestgröße
  1 px); echtes Ziehen mit der Maus über den `QObject`-Eventfilter
  (Press/Move/Release), `.pfm` wird beim Loslassen geschrieben – noch
  ohne sichtbare Raster-Einrastung/-Anzeige (Werte selbst liegen bereits
  auf dem 8-px-Raster, wenn per Tastatur bewegt; per Maus sind beliebige
  Pixelwerte möglich, Einrasten ist eine offene Verfeinerung)
- [x] Tastatur direkt im `eventFilter`: Pfeiltasten (`RASTER` = 8 px),
  Alt+Pfeil (1 px), Umschalt+Pfeil (Größe), Entf (`loeschen()`), Strg+D
  (`duplizieren()`, versetzt um `RASTER`, findet automatisch einen
  eindeutigen Attributnamen wie `b_ein_kopie`, `b_ein_kopie2`, …)
- [x] `loeschen()`: entfernt die Komponente vom Formular (`delattr`) und
  aus der Überwachung, wählt danach das Formular selbst aus
- [x] `DesignerCanvas(formular, pfm_pfad=...)` schreibt nach jeder
  Änderung automatisch die `.pfm` (Verschieben, Größe, Löschen,
  Duplizieren); in `HauptFenster.designer_oeffnen()` verdrahtet
- [ ] Komponente aus der Palette platzieren – braucht Schritt 6
  (Komponentenpalette), vorerst zurückgestellt; Serialisierung/Hinzufügen
  ist aber bereits bereit (dieselbe `duplizieren()`-Mechanik lässt sich
  wiederverwenden, sobald die Palette eine Komponente ohne Vorlage
  erzeugen soll)
- [ ] sichtbare Größenanfasser zum Ziehen (aktuell nur Tastatur-Resize)
  – offene Verfeinerung
- [x] Tests: `tests/test_designer_bearbeiten.py`, 14 Tests (u. a. echte
  simulierte Maus-Zieh-Sequenz über drei `QMouseEvent`s, automatisches
  Schreiben der `.pfm` geprüft); End-to-End von Hand geprüft: IDE
  starten, Ampel-Kopie öffnen, Komponente auswählen und verschieben,
  Änderung landet in der `.pfm` auf der Festplatte

### 5. Undo/Redo (Command-Pattern) — erledigt

- [x] `ide/designer/kommando.py`: `Kommando`-Protokoll (`tun`/
  `rueckgaengig`), `Kommandostapel` (Rückgängig-/Wiederholen-Stapel,
  neues Kommando leert den Wiederholen-Stapel), `EigenschaftKommando`
  deckt reine Eigenschaftsänderungen generisch ab (ermittelt den
  vorherigen Wert selbst statt mit Deltas zu rechnen – bleibt auch bei
  intern begrenzten Änderungen wie der Mindestgröße 1 px korrekt)
- [x] `DesignerCanvas.verschieben()`/`groesse_aendern()` laufen jetzt
  über `EigenschaftKommando`; Ziehen mit der Maus sammelt nur eine
  Live-Vorschau und erzeugt **ein** Kommando beim Loslassen (kein
  Kommando pro Pixel); `loeschen()`/`duplizieren()` über eigene, kleine
  Kommandos (`_LoeschenKommando`/`_DuplizierenKommando`), die das
  Qt-Widget beim Löschen nur trennen/verstecken statt zu zerstören,
  damit Rückgängig es wieder anzeigen kann
- [x] Strg+Z (rückgängig), Strg+Umschalt+Z bzw. Strg+Y (wiederholen) –
  wirken unabhängig davon, ob gerade eine Komponente ausgewählt ist
  (anders als Verschieben/Löschen/Duplizieren, die eine Auswahl
  brauchen)
- [x] Tests: `tests/test_kommando.py` (8, das Kommando-Muster
  eigenständig ohne `pcl`/Qt), `tests/test_designer_undo.py` (12, u. a.
  vollständiges Rückgängig einer Kette aus Verschieben/Größe ändern/
  Duplizieren/Löschen ergibt exakt den Ausgangszustand, Ziehen ist ein
  einziger Rückgängig-Schritt, gelöschte Komponente lässt sich nach dem
  Rückgängig-Machen weiterbearbeiten)
- **Zurückgestellt:** Menüeinträge „Rückgängig“/„Wiederholen“ im
  Bearbeiten-Menü (Abschnitt 7.2) – bräuchten eine Verfolgung, welcher
  Designer-Tab gerade aktiv ist; die Tastenkürzel funktionieren bereits
  vollständig, da Qt Tastaturereignisse an das fokussierte Widget im
  jeweils aktiven Tab liefert

### 7. Ereignis-Codegenerierung (libcst) — erledigt

- [x] `ide/codegen/ereignis.py`: `handler_methode_einfuegen(quelltext,
  klassenname, methodenname)` – reine Textumwandlung per `libcst`
  (`CSTTransformer`), fügt `def <methodenname>(self, sender): pass` am
  Ende der passenden Klasse ein; restlicher Quelltext (Kommentare,
  Docstrings, Formatierung) bleibt zeichengenau erhalten; bereits
  vorhandene Methode gleichen Namens wird nicht doppelt eingefügt,
  unbekannter Klassenname ändert nichts (Abschnitt 4.4)
- [x] `DesignerCanvas.ereignis_handler_erzeugen(komponente)`: bei
  Doppelklick (neuer `MouseButtonDblClick`-Zweig im `eventFilter`, der
  zuerst einen eventuell laufenden Ziehvorgang verwirft) – ermittelt das
  eindeutige Standardereignis des Komponententyps (`ereignisse(typ)` hat
  genau einen Eintrag, sonst No-op, z. B. bei `Label`/`Shape`), baut den
  Methodennamen `<attributname>_<ereignisname>` (z. B. `b_ein_on_click`),
  fügt ihn über `handler_methode_einfuegen()` in die zur `.pfm` gehörige
  `.py`-Unit ein (`unit_pfad = pfm_pfad.with_suffix(".py")`) und
  verknüpft ihn als gebundene Platzhaltermethode über ein normales
  `EigenschaftKommando` (damit Rückgängig/`.pfm`-Autospeichern wie bei
  jeder anderen Eigenschaftsänderung funktionieren); bereits verknüpftes
  Ereignis liefert nur den vorhandenen Namen zurück, ohne die Datei
  erneut zu ändern; ohne `pfm_pfad` (z. B. reine Vorschau) passiert
  nichts (`None`)
- [x] Tests: `tests/test_ereignis_codegen.py` (7, reine
  `libcst`-Textumwandlung: Einfügen, Idempotenz, Zeichentreue,
  unbekannte Klasse, `compile()`-Gültigkeit, `(self, sender)`-Signatur),
  `tests/test_designer_ereignis_generieren.py` (7, gegen
  `DesignerCanvas` mit `tmp_path`-Dateien: Methode wird in der Unit
  erzeugt und live verknüpft, kein doppeltes Einfügen, `.pfm` speichert
  den Ereignisnamen, Rückgängig entfernt nur die Verknüpfung nicht die
  Methode, echter simulierter Doppelklick über den `eventFilter`
  hinterlässt keinen offenen Ziehvorgang, Komponente ohne Ereignis bzw.
  ohne `pfm_pfad` ist ein No-op)

### 8. Abnahme: Ampel vollständig in der IDE erstellen — erledigt

- [x] Ampel-Formular ausschließlich über Designer + Inspektor + Palette
  nachbauen (nicht die vorhandene `.pfm` von Hand schreiben), Ergebnis
  mit `beispielprojekte/Ampel/` vergleichen
- **Beim Nachbauen zwei echte Lücken gefunden und behoben** (nicht nur
  Testaufbau, sondern echte Fehler in Schritt 7):
  1. Methodennamen für Ereignis-Handler enthielten das `on_`-Präfix des
     Ereignisnamens (`b_ein_on_click` statt `b_ein_click`), abweichend
     von der Konvention aus Abschnitt 4.4/9 und allen Beispielprojekten
     – behoben (`_ereignis_kurzname()` in `ide/designer/canvas.py`)
  2. Doppelklick auf das Formular selbst (statt auf eine Kind-
     Komponente) erzeugte keine Methode – die Ampel braucht aber
     `on_create: form_create` auf dem Formular. Jetzt erzeugt ein
     Doppelklick auf den leeren Formularhintergrund `form_create`
     ebenso wie ein Doppelklick auf eine Komponente dessen Ereignis
- **Neu, weil beim Nachbauen zwingend gebraucht:**
  `DesignerCanvas.komponente_umbenennen(komponente, neuer_name)` – die
  Eigenschaft „Name“ (Abschnitt 7.6) ist kein `Prop` der Komponente,
  sondern der Attributname im Formular; rückgängig machbar über ein
  eigenes Kommando wie die übrigen Struktur-Operationen. Ohne
  Umbenennen ließen sich nur generische Namen wie `button2` vergeben,
  keine sprechenden wie `b_einschalten` – die Ampel wäre nicht
  originalgetreu nachbaubar gewesen. **Noch offen:** eigene Zeile dafür
  in der `EigenschaftenTabelle` (bisher nur als Canvas-Methode
  nutzbar, siehe „Zurückgestellt“ unten)
- [x] Tests: `tests/test_designer_umbenennen.py` (7, `komponente_umbenennen`
  eigenständig: ändert das Attribut, No-op bei gleichem Namen, Fehler bei
  vergebenem Namen/ungültigem Bezeichner/Formular selbst, rückgängig
  machbar), `tests/test_m3_abnahme_ampel.py` (2: komplette Ampel wird
  ausschließlich über `komponente_platzieren`/`setattr`/
  `komponente_umbenennen`/`ereignis_handler_erzeugen` nachgebaut und
  gegen die echte `beispielprojekte/Ampel/u_main.pfm` verglichen – Typ,
  Position, Größe, Beschriftung, Ereignisse aller acht Kinder stimmen
  überein; alle vier erzeugten Ereignismethoden stehen kompilierbar in
  der Unit)

## Zurückgestellt innerhalb M3

- Mehrfachauswahl mit gemeinsamer Eigenschaftsänderung
- Ausrichten/Verteilen-Werkzeuge, Hilfslinien
- Favoriten-Reiter, „Geändert“-Reiter im Inspektor
- Vorschau hell/dunkel und mehrere Fenstergrößen im Designer
- „Name“ als eigene, editierbare Zeile in der `EigenschaftenTabelle`
  (Backend `DesignerCanvas.komponente_umbenennen()` steht bereits)
- Aufklappbare Untereigenschaften im Inspektor (z. B. `Shape.brush.color`,
  `font.size`) – bisher nur direkt im Code zuweisbar, keine eigene Zeile
