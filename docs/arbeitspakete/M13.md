# M13 – Vollwertige Installation und Installer

Auftrag (Nutzer, September 2026): „Der Installer soll alles beinhalten,
um das System vollumfänglich zu installieren. Eine Auswahl, wohin es
installiert werden soll, eine Lizenzseite, die man akzeptieren muss, die
klassischen Themen bei einer Windows-Installation. Beachte, dass in der
Exe, die daraus entsteht, alle Dinge komplett machbar sind, also auch
pip und den Rest.“

## Warum der bisherige Weg an eine Grenze stößt

Bis M12 war die ausgelieferte Natter ein **PyInstaller-Bundle**: ein
eingefrorener Python, aus dem sich nichts mehr herausnehmen lässt. Das
hat zwei Dinge dauerhaft unmöglich gemacht, und beide gehören zum
Funktionsumfang:

* **Paketverwaltung.** `pip` ist in einem eingefrorenen Python nicht
  vorhanden, und ein nachträglich installiertes Paket läge in einem
  Ordner, den das Bundle beim nächsten Start gar nicht ansieht.
* **„Als Exe exportieren“.** PyInstaller braucht eine vollständige,
  auseinandernehmbare Python-Installation, um daraus eine neue zu bauen.

In M12 haben beide deshalb ehrlich gemeldet, dass sie in der
installierten Fassung nicht arbeiten können. Das war richtig gegenüber
dem alten Aufbau – aber der Auftrag lautet jetzt, den Aufbau zu ändern.

## Der neue Aufbau

Statt Python einzufrieren wird eine **vollwertige, verschiebbare
CPython-Installation** mitgeliefert, auf der Natter *läuft*.

```
<Installationsordner>\
  Natter.exe              schlanker Starter (Icon, signiert)
  python\                 CPython 3.13 (python-build-standalone), mit pip
    python.exe            für Konsolenprogramme
    pythonw.exe           für die IDE und GUI-Programme
    Lib\site-packages\    ide, pcl, PySide6, pandas, numpy, … + pip + PyInstaller
                          templates\, docs\, design\, schemas\, beispielprojekte\
  Lizenzen\               LGPL-3.0 und die Lizenztexte aller Bibliotheken
  manifest.json           Prüfsummen (Abschnitt 17.8)
```

Die Python-Installation stammt von **python-build-standalone** (dieselbe
Quelle, aus der `uv python install` bedient wird): eine gewöhnliche,
ortsunabhängige CPython mit `pip`, 21 MB Download.

### Was damit von selbst wieder geht

| Funktion | Warum sie jetzt arbeitet |
|---|---|
| Paketverwaltung | Es ist ein echtes Python mit `pip` |
| Als Exe exportieren | PyInstaller liegt mit drin und findet einen auseinandernehmbaren Python |
| Schülerprogramm starten | `sys.executable` ist wieder ein echter Interpreter |
| Debugger, Vorstart-Prüfung | dito, ohne Sonderweg |

Der `--python`-Durchreicher aus M12 wird dadurch überflüssig. Er bleibt
trotzdem stehen: er kostet nichts und ist die Rückfallebene, falls
jemand doch wieder ein eingefrorenes Bundle baut.

**Ein Detail, das leicht schiefgeht:** die IDE läuft unter
`pythonw.exe` (ohne Konsolenfenster). Ein **Konsolen**programm muss
dagegen mit `python.exe` starten, sonst hat es keine Konsole, in die es
schreiben könnte. `python_befehl()` rechnet deshalb von `pythonw.exe`
auf `python.exe` zurück.

## Der Installer

Die klassischen Schritte einer Windows-Installation, in dieser
Reihenfolge:

1. **Willkommen** – Inno Setup 6 blendet diese Seite in der modernen
   Darstellung standardmäßig aus; sie wird ausdrücklich eingeschaltet
2. **Lizenz**, die angenommen werden muss – Natters eigene Lizenz und
   der Hinweis auf die Lizenzen der mitgelieferten Bibliotheken
3. **Zielordner wählen**
4. **Startmenü-Ordner wählen**
5. **Zusatzaufgaben**: Desktopsymbol, `.natter`-Dateien mit Natter öffnen
6. **Bereit zur Installation** mit Zusammenfassung
7. Fortschritt, **Fertigstellen** mit „Natter starten“
8. Deinstallation über „Apps & Features“

### Rechte auf einem Schulrechner

Voreinstellung bleibt die Installation **nur für den angemeldeten
Nutzer** (`%LOCALAPPDATA%\Programs\Natter`). Das ist auf einem
Schulrechner ohne Administratorrechte der einzige Weg, der funktioniert
– und nur dort darf `pip` später auch wirklich schreiben. Wer
systemweit installiert, braucht für die Paketverwaltung
Administratorrechte; die Meldung sagt das dann.

## Was erst die fertige Installation gezeigt hat

Vier Fehler standen in keinem Test und waren am Quellbaum nicht zu
sehen. Alle vier kamen erst zum Vorschein, als die gebaute Auslieferung
und danach eine echte Installation Schritt für Schritt benutzt wurden.

**1. Eine halb gefüllte Auslieferung, die fehlerfrei gebaut wurde.**
Auf dem Baurechner war `PYTHONUSERBASE` gesetzt (von der
Windows-Store-Python). Aus dieser Variablen rechnet *jede* Python 3.13
ihr Benutzer-Paketverzeichnis aus, also auch die frisch ausgepackte in
`dist`. Die sah die Pakete des Baurechners als ihre eigenen; `pip`
meldete Zeile für Zeile „Requirement already satisfied", installierte
nur Natter selbst und gab 0 zurück. In der fertigen Auslieferung
fehlten `ruff`, `scipy`, `scikit-learn`, `cryptography`, `setuptools`
und ein Dutzend weiterer Pakete – und damit die Prüfung vor dem Start,
die Integritätsprüfung und der Exe-Export. Aufgefallen ist es erst beim
**Nachzählen der Pakete** in `dist`, nicht am Bau.

Der Bau räumt diese Verweise jetzt aus der Umgebung und schaltet das
Benutzerverzeichnis ab. `tools/launcher.py` tut beim Start dasselbe:
sonst könnte eine fremde Python-Umgebung auf einem Schulrechner Natter
umwerfen, ohne dass dort jemand etwas an Natter geändert hätte.

**2. Die Integritätsprüfung lief in der Auslieferung gar nicht mehr.**
Sie erkannte eine gebaute Installation an `sys.frozen`. Das gibt es
seit M13 nicht mehr – Natter läuft als gewöhnliches
`pythonw.exe -m ide`. Bemerkt hätte das niemand, denn die Prüfung
meldet sich nur, wenn etwas nicht stimmt. Erkennungsmerkmal ist jetzt
das `manifest.json` neben der Exe.

**3. Sobald sie wieder lief, meldete sie ständig falschen Alarm.** Eine
echte Python-Installation legt beim ersten Import neben jedem Modul
eine `.pyc` an – über achtzig Stück, bevor überhaupt ein Fenster offen
war. Dazu kommt: was ein Schüler über das Menü „Pakete" installiert,
landet ganz normal in `site-packages`, und `pip` hebt dabei auch mal
numpy an. Übersetzte Module und die mitgelieferten Fremdbibliotheken
stehen deshalb nicht mehr unter Aufsicht; `Natter.exe`, die
mitgelieferte Python und Natters eigene Pakete schon.

**4. Der Uninstaller galt als eingeschleuste Datei.** Inno Setup legt
`unins000.exe` und `unins000.dat` neben `Natter.exe` – erst *während*
der Installation, also lange nachdem das Manifest beim Bau geschrieben
wurde. Jede frisch installierte Natter begrüßte den Schüler mit „Natter
wurde nach der Erstellung verändert" und der Aufforderung, neu zu
installieren; die neue Installation legte den Uninstaller prompt wieder
an.

Nebenbei kostete die schnelle Prüfung bei jedem Start 2,7 s, weil sie
durch alle dreißigtausend Dateien der mitgelieferten Python lief. Sie
sucht jetzt gezielt und braucht 0,07 s.

## Nachgemessen in der fertigen Installation

Alles über `pythonw.exe -m …` aus der installierten Fassung heraus,
nicht aus dem Entwicklungsbaum:

| Geprüft | Ergebnis |
|---|---|
| 24 Laufzeitpakete importierbar | vollständig |
| Paket nachinstallieren (`paket_installieren`) | lädt und installiert, danach in der Liste |
| Konsolenprogramm starten | läuft, Ausgabe kommt an, Rückgabewert 0 |
| GUI-Programm starten | Fenster bleibt offen, nichts auf stderr |
| Prüfung vor dem Start (`ruff`) | findet den Syntaxfehler und blockiert |
| Als Exe exportieren | baut, und die **exportierte Exe läuft** |
| Integritätsprüfung | schnell 0,07 s, vollständig 2,6 s, beide sauber |
| `Natter.exe` aus der Installation | startet `python\pythonw.exe -m ide`, Fenster „Natter" |

## Offen
