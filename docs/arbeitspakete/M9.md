# Arbeitspaket M9 – Diagramm-Editor

Siehe konzept-natter.md, Abschnitt 13 (Diagramm-Editor), 14 (Design-
Prüfer, Layout-Hinweise gelten sinngemäß). Kleinteilig wie M1–M8.

## Abnahmekriterium (aus dem Konzept)

UML-Klassendiagramm `TAmpel`, Struktogramm `ampel_zeichnen` und
Entscheidungstabelle der Ampel von Hand erstellen und als PDF
exportieren.

## Reihenfolge (Nutzer-Feedback September 2026)

Erst die MVP-Dreiergruppe aus dem Abnahmekriterium fertig und
abgenommen (Klassendiagramm, Struktogramm, Entscheidungstabelle),
danach Use-Case-, Aktivitäts-, Zustands- und Sequenzdiagramm als eigene
Schritte (Abschnitt 13.4: „Später“). Innerhalb der Dreiergruppe zuerst
das Fenster-Grundgerüst und das `.pdiag`-Format (beide werden von allen
drei gebraucht), dann das Klassendiagramm komplett (Formen → Bearbeiten
→ Verbindungen → Beschriften → Eigenschaften-Panel → Stilvorlagen/
Layout-Hinweise → Export/Druck – dieselbe Reihenfolge wie beim Designer
in M3: Anzeige vor Bearbeiten vor Verbindungen), zuletzt Struktogramm
und Entscheidungstabelle (strukturell näher an einer Baumstruktur bzw.
`StringGrid` als an Formen+Verbindungen, deshalb eigene Schritte statt
Wiederverwendung der Klassendiagramm-Canvas).

Fenster-Architektur (Nutzer-Feedback bestätigt): echtes zweites
Top-Level-Fenster mit eigenem Taskleisten-Eintrag, unabhängig vom
Hauptfenster verschiebbar (Abschnitt 13.1) – kein Dock/Tab in der IDE.

Export-Umfang (Nutzer-Feedback bestätigt): PNG, SVG, PDF und Drucken
gehören von Anfang an zum ersten fertigen Diagrammtyp, nicht erst
später nachgezogen.

### 2b. Ansicht: Zoom, Verschieben, Lineale, Minimap

- [x] **Rollen (Scrollen) waagerecht und senkrecht** – vom Nutzer
  gemeldet. Die Zeichenflächen steckten in keinem Rollbereich und
  hatten eine feste Mindestgröße von 640×480; alles außerhalb des
  Fensters war damit nicht erreichbar, obwohl allein ein A4-Blatt quer
  schon 1123 px breit ist. Jede Fläche rechnet jetzt ihre Inhaltsgröße
  aus (Blatt bzw. Blockbaum bzw. Tabelle, plus Rand) und steckt in
  einer `QScrollArea`. Derselbe Fehler steckte im **Formular-Designer**:
  ein Formular, das größer war als der Tab-Bereich, wurde abgeschnitten
  – dort ohne `widgetResizable`, weil die Größe eines Formulars eine
  vom Nutzer gesetzte Eigenschaft ist und nicht von der Fenstergröße
  abhängen darf
- [x] Zoom im Klassendiagramm: Strg+Mausrad, Strg++/Strg+-, Strg+0
  („Alles anzeigen“ – rechnet die Stufe aus dem Sichtfenster),
  Strg+1 („100 %“), begrenzt auf 25 %–400 %. Die Zoomstufe steht in
  der Statusleiste. Nur das **Zeichnen** skaliert; jede Trefferprüfung
  rechnet weiter in Diagrammkoordinaten, sonst müsste jede einzelne
  Funktion den Zoom kennen. Der Texteditor in der Form skaliert
  Feldgeometrie **und** Schrift mit, sonst läge er bei 200 % neben
  seiner Form
- [x] Ansicht verschieben mit Leertaste+Ziehen und mit der mittleren
  Maustaste; das Verschieben geht dem Auswählen vor. Während des
  Beschriftens bleibt die Leertaste ein Leerzeichen
- [ ] Zoom auch für Struktogramm und Entscheidungstabelle – dort sind
  die Menüeinträge bis dahin ausgegraut statt wirkungslos
- [ ] Lineale (der Seitenbereich selbst ist mit Schritt 7 erledigt)
- [ ] Minimap
- [ ] Menü „Ansicht“ aktivieren (Zoom, Raster, Lineale, Minimap,

### 12. UML-Klassen über einen Eigenschaften-Dialog bearbeiten

**Nutzer-Entscheidung September 2026, mit Bildschirmfotos belegt:** die
Inhalte einer UML-Klasse werden **nicht** direkt auf der Zeichenfläche
bearbeitet, sondern über einen Eigenschaften-Dialog mit Reitern – so
wie es das Programm Dia macht („Eigenschaften: UML – Class“). Wörtlich:
„so sollen die uml diagramme gebaut werden. es soll nicht in der
oberfläche direkt bearbeitbar sein.“

Damit ist die Formulierung im Konzept, Abschnitt 13.3 („bearbeitet
direkt in der Form“), überholt. Die Zeichenfläche bleibt zuständig für
**Anordnen** (platzieren, verschieben, Größe, verbinden), der Dialog
wird zuständig für **Inhalt**.

Warum das die bessere Lösung ist: ein Attribut ist kein Textschnipsel,
sondern hat Name, Typ, Vorgabewert und Sichtbarkeit; eine Operation
zusätzlich eine Parameterliste. Als freier Text ließ sich das weder
prüfen noch normgerecht darstellen – `+setzen(farbe: str)` war bisher
eine Zeichenkette, die zufällig wie UML aussah.

#### 12.1 Datenmodell umstellen

Attribute und Operationen werden aus freien Zeichenketten zu
strukturierten Einträgen. `schemas/pdiag.schema.json` wird entsprechend
erweitert (neue `$defs`), der bisherige `text`-Block mit
`attributes: [string]` und `methods: [string]` entfällt.

- [ ] `$defs/attribut`: `name`, `type`, `value`, `comment`,
  `visibility` (`public`/`private`/`protected`/`implementation`),
  `class_scope` (bool)
- [ ] `$defs/operation`: `name`, `type` (Rückgabetyp), `stereotype`,
  `comment`, `visibility`, `inheritance` (`abstract`/`virtual`/`leaf`),
  `class_scope` (bool), `query` (bool, „Anfrage“), `parameters`
- [ ] `$defs/parameter`: `name`, `type`, `default`, `comment`,
  `direction` (`undefined`/`in`/`out`/`inout`)
- [ ] `$defs/vorlagenparameter`: `name`, `type` (für Vorlageklassen)
- [ ] Klasse selbst zusätzlich: `stereotype`, `comment`, `abstract`,
  `template` (bool) und `template_parameters`
- [ ] Anzeigeschalter je Klasse, weil sie zum Diagramm gehören und
  nicht zur Stilvorlage: `attributes_visible`, `operations_visible`,
  `attributes_suppressed`, `operations_suppressed`,
  `comments_visible`, `wrap_operations`, `wrap_after_operations`
  (Vorgabe 40), `wrap_after_comments` (Vorgabe 17),
  `show_documentation`
- [ ] **Migration:** vorhandene `.pdiag` mit den alten Textlisten
  müssen weiter ladbar bleiben. Beim Laden werden Zeilen wie
  `-__zustand: int` bzw. `+get_zustand(): int` einmalig in die neue
  Struktur zerlegt (führendes `+`/`-`/`#`/`~` → Sichtbarkeit, Teil vor
  `:` → Name, danach → Typ, Klammern → Operation mit Parametern). Ein
  eigener Test deckt genau diese Umsetzung ab, und die drei
  Abnahmediagramme in `beispielprojekte/Ampel/diagramme/` werden
  danach einmal neu geschrieben

#### 12.2 Der Dialog

Ein modaler Dialog mit fünf Reitern, unten die drei Knöpfe
**Schließen**, **Anwenden**, **OK** (Anwenden übernimmt, ohne zu
schließen). Geöffnet wird er per Doppelklick auf die Form, per F2 und
über „Bearbeiten → Eigenschaften …“.

- [ ] **Reiter „Klasse“:** Klassenname, Stereotyp, Kommentar
  (mehrzeilig); Schalter „Abstrakt“, „Attribute sichtbar“,
  „Operationen sichtbar“, „Operationen umbrechen“, „Kommentare
  sichtbar“, „Dokumentationsauszeichnung anzeigen“; rechts daneben
  „Attribute unterdrücken“, „Operationen unterdrücken“ und zwei
  Zahlenfelder „Umbruch nach dieser Länge“ (für Operationen und für
  Kommentare)
- [ ] **Reiter „Attribute“:** Liste der Attribute mit den Knöpfen
  **Neu**, **Löschen**, **Hoch**, **Runter**; darunter die Gruppe
  „Attributdaten“ mit Name, Typ, Wert, Kommentar, Sichtbarkeit
  (Auswahlfeld) und „Klassen-Gültigkeitsbereich“. Die Felder sind
  ausgegraut, solange nichts ausgewählt ist
- [ ] **Reiter „Operationen“:** Liste wie bei den Attributen; Gruppe
  „Operationsdaten“ mit Name, Typ, Stereotyp, Sichtbarkeit, Typ der
  Vererbung, „Klassen-Gültigkeitsbereich“, „Anfrage“ und Kommentar;
  darunter eine **eigene Parameterliste** (Neu/Löschen/Hoch/Runter)
  mit der Gruppe „Parameterdaten“: Name, Typ, Vorgabewert, Richtung,
  Kommentar
- [ ] **Reiter „Vorlagen“:** Schalter „Vorlageklasse“, Liste der
  formellen Parameter mit Neu/Löschen/Hoch/Runter und der Gruppe
  „Formelle Parameterdaten“ mit Name und Typ
- [ ] **Reiter „Stil“:** Füllung, Linie und Schriftgröße – das, was
  heute im Eigenschaften-Bereich rechts steht (Schritt 6). Der Bereich
  rechts bleibt für Position und Größe zuständig, weil man die beim
  Anordnen laufend braucht
- [ ] Ein Dialogdurchgang ist **ein** Undo-Schritt, egal wie viele
  Felder geändert wurden. „Anwenden“ mehrfach ergibt entsprechend
  mehrere Schritte
- [ ] „Schließen“ verwirft, was seit dem letzten „Anwenden“ geändert
  wurde

### 13. Klasse als Python-Quelltext ausgeben

**Nutzer-Wunsch September 2026:** aus einer im Diagramm modellierten
Klasse soll sich der passende Python-Quelltext erzeugen lassen – **in
eine eigene Datei oder in ein Fenster, je nach Auswahl** –, um ihn von
dort zu übernehmen.

Das ist der eigentliche Gewinn aus Schritt 12: erst weil Attribute und
Operationen strukturiert vorliegen (Name, Typ, Sichtbarkeit,
Parameter), lässt sich daraus überhaupt sinnvoller Code erzeugen. Aus
freiem Text ginge es nicht.

Dia kann das übrigens auch, über XSLT-Vorlagen
(`dia-uml2python.xsl`, dazu Java, C++, C, IDL). Dessen Ausgabe ist
allerdings alt: Sichtbarkeit als Kommentar (`#private:`), keine
Typangaben, `return None` als Rumpf. Natter erzeugt stattdessen
Quelltext im Stil der eigenen Beispielprojekte.

#### 13.1 Was erzeugt wird

Maßstab ist `beispielprojekte/Ampel/u_ampel.py` – so sieht in diesem
Projekt handgeschriebener Code aus, und so soll auch der erzeugte
aussehen:

```python
class Ampel:
    """Eine Ampel mit vier Zuständen."""

    def __init__(self, eingeschaltet: bool, zustand: int) -> None:
        self.__eingeschaltet = eingeschaltet
        self.__zustand = zustand

    def einschalten(self) -> None:
        ...
```

- [ ] Sichtbarkeit über die Namensschreibweise statt über Kommentare:
  `private` → `__name`, `protected` → `_name`, `public` → `name`
- [ ] Typangaben aus dem UML-Typ übernehmen (`zustand: int`,
  `-> bool`); fehlt der Typ, wird die Angabe weggelassen statt
  geraten
- [ ] `__init__` aus den Attributen erzeugen, mit den Vorgabewerten
  aus dem Feld „Wert“
- [ ] Kommentare aus dem Dialog werden zu Docstrings
- [ ] Operationsrümpfe bleiben leer (`...`), damit niemand denkt, hier
  stünde schon Logik. Abstrakte Operationen bekommen zusätzlich
  `raise NotImplementedError`
- [ ] Klassen-Gültigkeitsbereich → `@staticmethod` bzw.
  Klassenattribut; „Anfrage“ → `@property`, wenn die Operation keine
  Parameter hat
- [ ] Vererbung aus den Verbindungen: eine **Verallgemeinerung** wird
  zur Basisklasse (`class TAmpel(Fahrzeug):`), eine **Realisierung**
  ebenso. Aggregation und Komposition werden zu Attributen
- [ ] Vorlageklassen (Reiter „Vorlagen“) → `typing.Generic`
- [ ] Deutsche Umlaute in Namen bleiben erhalten – Python erlaubt sie,
  und in dieser Zielgruppe kommen sie vor

#### 13.2 Bedienung

- [ ] Neuer Menüeintrag „Klasse → Quelltext erzeugen …“ (bzw. im
  Kontextmenü der Form), aktiv nur bei Klassendiagrammen
- [ ] Ein kleiner Dialog fragt zweierlei:
  - **Ziel:** „In einem Fenster anzeigen“ oder „In eine Datei
    schreiben“
  - **Umfang:** „Nur die ausgewählte Klasse“ oder „Alle Klassen des
    Diagramms“
- [ ] Die getroffene Wahl wird als Vorgabe für das nächste Mal
  gemerkt (`QSettings`, wie die übrigen Einstellungen)

#### 13.3 Ausgabe in ein Fenster

- [ ] Ein eigenes Fenster mit dem erzeugten Quelltext, **nur
  lesbar** – es ist eine Vorlage zum Übernehmen, kein zweiter Editor
- [ ] Syntaxhervorhebung über den vorhandenen `QuelltextEditor`
  (`ide/shell/quelltexteditor.py`), damit es aussieht wie im Editor
- [ ] Knöpfe: **Kopieren** (alles in die Zwischenablage),
  **Speichern unter …** und **Schließen**
- [ ] Mehrere Klassen kommen nacheinander in dieselbe Ansicht, durch
  Leerzeilen getrennt

#### 13.4 Ausgabe in eine Datei

- [ ] Vorschlag: `units/<klassenname>.py` im aktuellen Projekt,
  kleingeschrieben, mit `u_`-Präfix passend zur Projektkonvention
- [ ] Eine **vorhandene Datei wird nie stillschweigend überschrieben**
  – es gibt eine Rückfrage mit den drei Möglichkeiten „Überschreiben“,
  „Anderen Namen wählen“ und „Abbrechen“. Wer eine Klasse zweimal
  erzeugt, soll nicht seine ausformulierten Methodenrümpfe verlieren
- [ ] Nach dem Schreiben erscheint die Datei im Projekt-Explorer und
  wird auf Wunsch gleich im Editor geöffnet
- [ ] Bei „Alle Klassen“ je Klasse eine eigene Datei

#### 13.5 Was bewusst nicht gemacht wird

- [ ] **Kein Rückweg** von Code zu Diagramm und kein Abgleich in
  beide Richtungen. Das wäre ein eigenes, großes Thema und geht in
  Schulprojekten regelmäßig schief, sobald jemand den erzeugten Code
  von Hand weiterschreibt
- [ ] **Kein Einfügen in bestehende Dateien.** Erzeugt wird immer eine
  vollständige, frische Datei; das Zusammenführen bleibt Handarbeit –
  dafür ist die Fensterausgabe zum Kopieren da

#### 13.6 Tests

- [ ] Je ein Test für Sichtbarkeit, Typangaben, Vorgabewerte,
  Docstrings, abstrakte Operationen, `@staticmethod`, `@property`
- [ ] Vererbung: Verallgemeinerung wird zur Basisklasse; zwei
  Basisklassen ergeben Mehrfachvererbung in der Reihenfolge der
  Verbindungen
- [ ] Der erzeugte Quelltext ist **gültiges Python**: `ast.parse()`
  über jedes Ergebnis, zusätzlich `ruff check` über eine erzeugte
  Beispieldatei
- [ ] Das `TAmpel`-Abnahmediagramm erzeugt eine Klasse, deren
