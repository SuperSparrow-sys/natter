# Arbeitspaket M4 – Debugger, Fehlerkatalog, Tests

Siehe konzept-natter.md, Abschnitt 8 (Debugger und Fehlermeldungen), 8.6
(Test-Explorer), 19 (Teststrategie). Kleinteilig wie M1–M3.

## Abnahmekriterium (aus dem Konzept)

Fehlerbeispiele liefern korrekte Meldungen, Breakpoints/Step
funktionieren, Tests mit Soll-/Ist-Anzeige.

## Reihenfolge

Fehlerkatalog zuerst, weil er ohne Debugger allein funktioniert und
testbar ist (reine Zuordnung Exception → Wo/Was/Prüfe-Text, Abschnitt
8.3–8.5) – der DAP-Client braucht ihn später für unbehandelte Ausnahmen.
Danach der DAP-Client selbst, aufgeteilt in Grundgerüst (Prozess starten,
Handshake), Ausführungssteuerung (Breakpoints/Step) und Variablen/
Aufrufstapel, jeweils zuerst gegen echtes `debugpy` über die reine
Client-Klasse getestet, ohne UI. Zuletzt die IDE-Verdrahtung (Ränder-
Breakpoints im Editor, Panels, Start mit Debugger) und, weitgehend
unabhängig, der Test-Explorer. Ruff-Prüfung vor Start ist eigenständig
und passt an beliebiger Stelle, hier zuerst, weil trivial.

**Kein VS Code nötig:** `prototypes/s3_debugpy` sah eine manuelle
Prüfung mit VS Code als DAP-Frontend vor (Abschnitt 23.3). Der echte
DAP-Client, den wir hier bauen, spricht direkt mit `debugpy` über Sockets
– das ist zugleich die rigorosere, automatisierte Version derselben
Prüfung (reproduzierbar in der Testsuite statt einmalig von Hand), macht
die manuelle S3-Prüfung also überflüssig.

`debugpy` steht bisher nur in der `prototypes`-Abhängigkeitsgruppe
(`pyproject.toml`); wird mit Schritt 3 in die echten `dependencies`
verschoben, weil der Debugger zur Laufzeit der IDE gehört, nicht nur zum
Prototyp.

### 1. Ruff-Prüfung vor Start

- [ ] `ide/run/`: vor `projekt_starten()` `ruff check` auf das Projekt
  laufen lassen (Abschnitt 8.2); Syntaxfehler, unbekannte Namen, fehlende
  Importe, ungenutzte Variablen
- [ ] Fehler landen im Panel „Meldungen“ (Datei, Zeile, Meldungstext);
  Start wird bei Fehlern nicht ausgeführt, nur bei Warnungen
- [ ] Test: Projekt mit absichtlichem Syntaxfehler wird nicht gestartet,
  sauberes Projekt schon

### 2. Fehlerkatalog

- [ ] `ide/debugger/fehlerkatalog.py`: Zuordnung Exception-Typ (+
  Kontext wie `__attribut`, Komma in `float()`) → Wo/Was/Prüfe-Text
  (Abschnitt 8.3–8.5), Katalog aus der Tabelle in 8.5 als MVP-Umfang
- [ ] Formatierung exakt im Aufbau aus 8.3 (Wo/Was/Prüfe, Datei/Zeile/
  Methode, Spaltenmarkierung ab Python 3.11 aus `SyntaxError`/
  `traceback`-Objekten)
- [ ] Python-eigene „Did you mean …?“-Zusätze an `NameError`/
  `AttributeError`-Meldungen werden entfernt (Abschnitt 8.4)
- [ ] Test: jeder Katalogeintrag liefert für ein Beispielprogramm mit
  diesem Fehler die drei Teile; entfernte „Did you mean“-Zusätze geprüft

### 3. DAP-Client: Grundgerüst

- [ ] `debugpy` von `prototypes`- in echte `dependencies` verschieben
- [ ] `ide/debugger/dap_client.py`: startet das Schülerprogramm über
  `debugpy` (eigener Prozess, Abschnitt 7.8), verbindet sich per Socket,
  führt den `initialize`/`launch`-Handshake nach DAP durch
- [ ] Nachrichtenrahmen (`Content-Length`-Header + JSON) senden/
  empfangen, Requests/Responses/Events sauber auseinandergehalten
- [ ] Test: gegen echtes `debugpy` (kein Mock) – Handshake erfolgreich,
  Prozess läuft und lässt sich sauber beenden

### 4. DAP-Client: Breakpoints und Ausführungssteuerung

- [ ] `setBreakpoints`, `continue`, `pause`, `next` (Einzelschritt),
  `stepIn` (Prozedurschritt), `stepOut` (bis Rücksprung), Breakpoint bei
  Zeile X „bis Cursor“ (Abschnitt 8.1)
- [ ] Anhalten bei unbehandelten Ausnahmen (`exceptionBreakpoints`),
  auch innerhalb von Ereignis-Handlern
- [ ] Test: Breakpoint in einer Testdatei hält den Prozess an der
  richtigen Zeile an, jede Schrittart bewegt die Ausführung korrekt
  weiter, unbehandelte Ausnahme hält ebenfalls an

### 5. DAP-Client: Variablen und Aufrufstapel

- [ ] `variables`/`scopes`-Requests: lokale Variablen, `self` mit
  Komponenten (nur `text`/`caption`/`checked`/`item_index` u. Ä., nicht
  alle internen Qt-Attribute), aufklappbare eigene Objekte (Abschnitt
  8.1)
- [ ] Überwachte Ausdrücke (`evaluate`-Request)
- [ ] Aufrufstapel mit `justMyCode`: `pcl`- und Qt-interne Frames
  ausgeblendet
- [ ] Test: Variablenwerte an einem Breakpoint stimmen mit dem
  tatsächlichen Programmzustand überein, Aufrufstapel enthält keine
  `pcl`-/Qt-Frames

### 6. IDE-Verdrahtung

- [ ] Ränder-Breakpoints im `QuelltextEditor` (Klick in den
  Zeilennummernrand setzt/entfernt einen Breakpoint, rote Markierung)
- [ ] Panels „Variablen“ und „Aufrufstapel“ (bisher Platzhalter in
  `HauptFenster.panels`) an den laufenden `DapClient` angebunden
- [ ] „Start“ vs. „Starten ohne Debugger“ (Abschnitt 7.8): Start hängt
  den DAP-Client ein, Strg+F5 nicht; Pause/Fortsetzen/Einzelschritt/
  Prozedurschritt/bis Rücksprung als Aktionen mit Symbolen
- [ ] Unbehandelte Ausnahme zeigt die Fehlerkatalog-Meldung im Panel
  „Meldungen“ und als Markierung an der Fehlerzeile im Editor
- [ ] Test: Breakpoint per Editor-Klick gesetzt hält den echten Prozess
  an, Variablen-Panel füllt sich, Fehlerkatalog-Meldung erscheint bei
  einer echten unbehandelten Ausnahme im Beispielprogramm

### 7. Test-Explorer

- [ ] Vorlage „Test-Unit“ im Neu-Dialog (`test_*.py`, `unittest`)
- [ ] Panel „Tests“ (bisher fehlt komplett, `PANEL_REITER` erweitern):
  Baum aus Dateien/Klassen/Testmethoden, Status (bestanden/
  fehlgeschlagen/Fehler), Laufzeit
- [ ] Einzelnen Test/Datei/alle Tests ausführen; Test mit Debugger
  starten (nutzt Schritt 3–5)
- [ ] Soll-/Ist-Anzeige bei fehlgeschlagenem `assertEqual` (`Soll: 50 ·
  Ist: 45`), Sprung zur Zeile
- [ ] Testergebnisse als HTML exportieren
- [ ] Test: Beispieltestdatei mit einem bestehenden und einem
  fehlschlagenden Test liefert im Baum den richtigen Status und die
  richtige Soll-/Ist-Anzeige

### 8. Abnahme: Fehlerbeispiele, Breakpoints/Step, Tests

- [ ] Für jeden Katalogeintrag aus Schritt 2 ein Beispielprogramm, das
  genau diesen Fehler auslöst – Meldung im Panel „Meldungen“ stimmt
- [ ] Ein Beispielprojekt (z. B. Ampel) mit Breakpoint in einem
  Ereignis-Handler starten, anhalten, Variablen prüfen, weiter schritten
- [ ] Eine Testdatei mit gemischten bestehenden/fehlschlagenden Tests im
  Test-Explorer ausführen, Soll-/Ist-Anzeige prüfen
